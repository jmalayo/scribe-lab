# scribe-lab (retrieval-augmented generation)

[![ci](https://github.com/jmalayo/scribe-lab/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/jmalayo/scribe-lab/actions/workflows/ci.yml)

Laboratorio de experimentos para un sistema RAG (Retrieval-Augmented Generation) en español, sobre un corpus técnico propio (`music-tagger`, [audio-intensity-lab](https://github.com/jmalayo/audio-intensity-lab)). Cada carpeta es un experimento incremental — chunking, hybrid search, reranking y evaluación de LLM-judge — que se evalúa contra un set de preguntas con respuestas conocidas (gold spans, `shared/eval/questions/`), y cada uno documenta su resultado en su propio README. Desde el 2026-10-18 el set tiene 135 preguntas, un archivo por tipo de pregunta. Los experimentos 1 a 3 y 5 están medidos con ese set; el 4 sigue con el set anterior de 34.

## Stack

- **Qdrant** — vector store para la búsqueda densa (`docker-compose-dev.yml`, puerto `6333`).
- **Text Embeddings Inference (HuggingFace)** — sirve el modelo de embeddings `paraphrase-multilingual-MiniLM-L12-v2` como servicio HTTP (`docker-compose-dev.yml`, puerto `1010`).
- **Ollama** — sirve los LLM de generación y de juez (`docker-compose-dev.yml`, puerto `1014`).
- **LettuceDetect** (`detector/`) — servicio FastAPI propio con `KRLabsOrg/lettucedect-210m-eurobert-es-v1` para detectar alucinación por span (`docker-compose-dev.yml`, puerto `1011`, perfil `eval`).
- **NLI** (`detector/nli_app.py`) — servicio FastAPI propio con `MoritzLaurer/mDeBERTa-v3-base-xnli-multilingual-nli-2mil7`, misma imagen que LettuceDetect (`docker-compose-dev.yml`, puerto `1012`, perfil `nli`).
- **MLflow** — tracking de cada corrida de cada experimento (`docker-compose-dev.yml`, puerto `5000`).
- **Postgres 17** — base relacional para los resultados de evaluación (`docker-compose-dev.yml`, `pgvector/pgvector:0.8.1-pg17`, puerto `1015`) y para las consultas del servicio (`docker-compose-prod.yml`, `postgres:17`, sin puerto publicado). El esquema se versiona con Alembic (`migrations/`) y se accede con SQLAlchemy (`shared/db.py`).
- **Arize Phoenix** (`version-21.0.0`) — recibe las trazas OpenTelemetry de la API (`docker-compose-prod.yml`, `127.0.0.1:1016`).
- **n8n** (`2.45.7`) — corre el canario diario contra `/v1/query` (`docker-compose-prod.yml`, `127.0.0.1:1017`, flujo en `n8n/canario.json`).

Todos los servicios corren vía `docker-compose up` y se reutilizan entre experimentos.

### Entorno de desarrollo

```bash
pip install -r requirements.txt
pre-commit install   # activa `ruff check` antes de cada commit y los tests unitarios antes de cada push (los ganchos son locales, no se versionan)
pytest tests/unit --cov=shared --cov-report=term-missing
docker compose -f docker-compose-dev.yml up -d postgres
alembic upgrade heads   # crea las tablas de las dos ramas (evaluacion y servicio) en el Postgres local
pytest tests/integration
```

Las reglas de `ruff` están en `ruff.toml`. El CI (`.github/workflows/ci.yml`) corre en cada push `ruff check .`, `lint-imports` y los tests unitarios con cobertura, y falla si `shared/eval/metrics.py` o `shared/retrieval.py` bajan de 80 %. Los tests unitarios no usan red ni modelos: el embedder, el LLM y el cross-encoder se reemplazan por dobles, y Qdrant se reemplaza por dobles o corre en memoria (`QdrantClient(":memory:")`, en los tests de indexado). El gancho de pre-push (`.pre-commit-config.yaml`) corre lo mismo que el CI, salvo `ruff`, que ya se verifica al hacer commit: `pytest tests/unit` con cobertura y el mínimo de 80 %. Si algo falla, el push se cancela antes de subir nada. Usa el `python` del `PATH`, así que hay que hacer el push con el entorno virtual activado; sin él, el gancho falla y el push también se cancela. Los tests de integración (`tests/integration`) crean una base descartable en Postgres, aplican las migraciones y prueban la API, el indexado, la búsqueda y el servidor MCP contra un Qdrant real, con el embedder y el LLM simulados; se saltean si Postgres o Qdrant no están levantados. En GitHub corren en el job `integration` de `ci.yml`, con Postgres 17 y Qdrant `v1.19.1` como contenedores, en los PR hacia `main` y a mano (`workflow_dispatch`). El gate de evaluación (`.github/workflows/eval.yml`) corre en los PR con la etiqueta `eval` o a mano: indexa `corpus_demo/` con TEI en CPU, calcula el acierto por pregunta en el top 10 de las 135 preguntas y bloquea si se pierden más preguntas de las que se ganan frente a `shared/eval/gate_baseline.csv` con McNemar exacto p < 0.05.

### Modelo de embeddings (descarga previa requerida)

El servicio `embedder` corre con `HF_HUB_OFFLINE=1` (no descarga nada en runtime), así que el modelo debe existir en `./embedder_cache/` **antes** de levantar el stack:

```bash
huggingface-cli download sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2 \
  --local-dir ./embedder_cache/models--sentence-transformers--paraphrase-multilingual-MiniLM-L12-v2 \
  --include "*.safetensors" "*.json" "sentencepiece.bpe.model" "tokenizer*" "1_Pooling/*" "2_Dense/*"
```

**Problema:** sin `--include`, el comando descarga *todos* los formatos del repo (pytorch, tensorflow, onnx x6, openvino x2) — **4.4 GB** — cuando TEI solo usa el safetensors + tokenizer. Con el filtro, baja a **~470 MB**.

## Matemática usada en el proyecto

Recuperación en `shared/retrieval.py`, métricas en `shared/eval/metrics.py`, verificación de respuestas en `shared/eval/grounding.py` y `detector/`. Cada técnica indica qué pregunta responde.

**Recuperación (qué chunks recibe el LLM)**

- **Similitud coseno** (Qdrant, `Distance.COSINE` en `shared/ingest.py`) — ¿qué tan cerca en significado están la pregunta y un chunk? Mide el ángulo entre sus vectores de embeddings, sin importar su largo. Solo compara vectores del mismo modelo de embeddings.
- **BM25 / Okapi BM25** (`BM25Index`) — ¿qué chunks comparten las palabras exactas de la pregunta? El término `log(1 + (n - freq + 0.5) / (freq + 0.5))` es el **IDF (Inverse Document Frequency)**: pesa más los términos raros del corpus. `k1 = 1.5` satura la repetición de un término y `b = 0.75` penaliza los chunks largos.
- **RRF / Reciprocal Rank Fusion** (`reciprocal_rank_fusion`) — ¿cómo combinar dos rankings cuyos scores no son comparables (coseno contra BM25)? Suma `1/(k+rank+1)` por lista, usando solo la posición (ver `experiments/hybrid-search/docs/README.md`).
- **Cross-encoder reranking** (`rerank`) — a diferencia de dense/BM25, que puntúan pregunta y chunk por separado, el cross-encoder procesa el par `(pregunta, chunk)` junto en un solo forward pass y devuelve un score de relevancia. Es más caro por candidato y más preciso para reordenar un pool reducido. `ms-marco` devuelve un **logit** (sin acotar, solo sirve para ordenar), no una probabilidad. El pipeline vigente no lo usa (experimento N.º 3).

**Verificación de respuestas (qué oraciones no tienen sustento)**

- **NLI, clasificación de pares** (`detector/nli_app.py`, `nli_scores`) — ¿el chunk (premisa) respalda, contradice o no dice nada sobre la oración (hipótesis)? mDeBERTa clasifica cada par en `entailment`, `neutral` o `contradiction`. Por oración se toma la mayor implicación y la mayor contradicción entre los 10 chunks.
- **Softmax** (`logits.softmax(-1)`) — convierte los tres puntajes crudos del NLI en probabilidades que suman 1 entre clases excluyentes.
- **Clasificación por token** (LettuceDetect, `sentence_scores`) — ¿qué tramo de la respuesta parece inventado? El modelo da una probabilidad por token con su rango de caracteres, y la oración toma la probabilidad más alta de sus tokens.

**Evaluación (qué tan bien funciona cada pieza)**

- **Coincidencia difusa de cadenas** (`rapidfuzz.fuzz.partial_ratio_alignment`) — ¿el gold span aparece en el chunk aunque difieran espacios, saltos de línea o cortes? Similitud de Levenshtein ≥ 0.8 y cobertura del span ≥ 0.9 (`shared/eval/EVAL_METHODOLOGY.md`).
- **Recall@k / MRR@k** — métricas estándar de IR: si el chunk correcto aparece entre los primeros k resultados (recall), y en qué posición (MRR, recíproco del rank).
- **Precisión y recall de un detector** (fase 2 del experimento N.º 4) — de las oraciones que marca, ¿cuántas tenían problema? Y de las que tenían problema, ¿cuántas marca? Se calculan contra la etiqueta humana por oración.
- **AUROC** (fase 2 del experimento N.º 4) — ¿qué tan bien ordena un score los positivos por encima de los negativos, sin elegir umbral? Es la proporción de pares (positivo, negativo) bien ordenados: 0.5 es azar y 1.0 es separación perfecta.
- **Intervalo de Wilson** (`wilson_ci`) — ¿entre qué valores está una proporción medida en pocas preguntas? A diferencia del intervalo normal, no se sale de [0, 1] ni se anula cuando hay 0 o n aciertos. Acota las abstenciones falsas del agente en el experimento N.º 5.
- **Bootstrap CI** (`bootstrap_ci`) — remuestreo con reemplazo (1000 veces) sobre los aciertos por pregunta para estimar un intervalo de confianza del 95 %, sin asumir una distribución normal.
- **McNemar exacto** (en los `ANALYSIS.md` de hybrid-search y reranking) — ¿la diferencia entre dos métodos sobre las mismas preguntas es real o azar? Solo cuentan las preguntas donde discrepan, y su reparto se contrasta con una binomial al 50 %. Su potencia, calculada sumando la binomial sobre los pares discordantes, fijó las 64 comparativas nuevas del experimento N.º 5.
- **Regla de decisión fijada de antemano** (`get_best_run` en `shared/tracking.py`) — `recall@10` con desempate por `mrr@10`, escrita antes de ver los resultados para no elegir la métrica que favorece al método preferido.

## Experimentos realizados

- **Experimento N.º 1 (chunking)** — resuelto en 6 fases; la última, el recálculo con 135 preguntas del 2026-10-25. Estado vigente en `experiments/chunking/docs/README.md` (fases en `PHASES.md`, análisis en `ANALYSIS.md`), config final en `experiments/chunking/results/best_config_135q.json`. Mejor config (dinámica + tablas separadas del embedding, evaluada con `fuzzy_actual`): `chunk_size=293`, `overlap=25%` → `recall@10=0.637`, `mrr@10=0.408` (con 34 preguntas ganaba `284/25%`, `recall@10=0.765`; las dos rinden igual sobre las 135, McNemar 1/1), con `recall@10` como métrica de decisión (el pipeline le pasa 10 chunks al LLM) y el criterio de acierto y el ground truth auditados en `shared/eval/EVAL_METHODOLOGY.md`. Reemplaza la config `512/25%` de la fase 1 (`recall@5=0.471`), inválida por truncación silenciosa contra el límite de tokens del embedder (ver `ANALYSIS.md` del experimento).
- **Experimento N.º 2 (hybrid search)** — resuelto en 5 fases; la última, el recálculo con 135 preguntas del 2026-10-25. Estado vigente en `experiments/hybrid-search/docs/README.md` (fases en `PHASES.md`, pruebas pareadas en `ANALYSIS.md`), resultados en `experiments/hybrid-search/results/results_135q.json`. Mejor método: `hybrid_rrf` → `recall@10=0.659`, `mrr@10=0.466`, sobre la config de chunking `293/25%`. Frente a `dense` (0.637) acierta 8 preguntas más y 5 menos, sin diferencia significativa (McNemar p=0.581). Con 34 preguntas había ganado `dense` por desempate en `mrr@10`.
- **Experimento N.º 3 (reranking)** — resuelto en 6 fases; la última, el recálculo con 135 preguntas del 2026-10-25. Estado vigente en `experiments/reranking/docs/README.md` (fases en `PHASES.md`, pruebas pareadas en `ANALYSIS.md` y `results/paired_135q.json`), resultados en `experiments/reranking/results/results_135q.json`. Sobre los 20 candidatos de `hybrid_rrf`, `BAAI/bge-reranker-v2-m3` sube `recall@10` de 0.659 a 0.733 (gana 11 preguntas y pierde 1, McNemar p=0.006) y `mrr@10` de 0.469 a 0.592, pero el servicio local no lo usa: en CPU tarda 4.05 s de p50 por consulta (`results/latency_cpu_135q.json`), contra ~190 ms en GPU. Tampoco se usa en la nube, porque la Lambda no tiene GPU.
- **Experimento N.º 4 (evaluación de respuestas)** — en curso, sin resultado final. Estado vigente en `experiments/evaluation/docs/README.md` (fases en `PHASES.md`, análisis en `ANALYSIS.md`). Fase 1: auto-juicio vs. juicio cruzado entre `llama3.2:3b` y `deepseek-r1:7b`; los jueces no coinciden entre sí (acuerdo en groundedness de 23–31 %), así que un `TRUE`/`FALSE` por respuesta no sirve como referencia. Fase 2 (vigente): respuestas de `llama3.1:8b` generadas con el retrieval vigente, etiquetadas a mano por oración, contra las que se calibran detectores especializados (LettuceDetect, NLI con mDeBERTa y `qwen3:8b` como juez de relevancia).
- **Experimento N.º 5 (agente contra pipeline fijo)** — resuelto: el servicio sigue con el pipeline. Estado vigente en `experiments/agent/docs/README.md` (integración MCP verificada en `MCP_INTEGRATION.md`), etiqueta humana en `experiments/agent/results/exp_2/verdicts_manual.csv`. Con `llama3.1:8b` en los dos lados y la misma recuperación (`/v1/retrieve`), sobre las 135 preguntas, el agente LangGraph no gana en las 64 comparativas nuevas, que es donde podía ganar: el pipeline acierta 5 que el agente no y el agente 2 que el pipeline no (McNemar exacto p=0.453). En total acierta 34 de 115 contra 41 del pipeline, usa 1995 tokens por pregunta contra 969 y tarda 2.4 s de p50 contra 1.3 s. Los dos se abstienen bien en 17 de las 20 preguntas sin respuesta. El juez `qwen3:8b` coincide con la etiqueta humana en 197 de 270 (kappa 0.635). La primera corrida, con 34 preguntas (`exp_1`), queda como antecedente en el mismo README.
- **Experimento N.º 6 (memoria conversacional)** — memoria adoptada en el servicio. Estado vigente en `experiments/conversation/docs/README.md` (fases en `PHASES.md`, análisis en `ANALYSIS.md`), resultados en `experiments/conversation/results/`. Acumular el historial en la consulta empeora la búsqueda de las preguntas que se entienden solas (fase 1). Sobre 41 conversaciones de `shared/eval/multiturn/`, en los 28 seguimientos que necesitan historial, `hybrid_rrf` acierta 17 con el seguimiento literal, 21 con la pregunta reescrita por `llama3.2:3b` (2/6, p=0.289) y 25 con la pregunta autónoma (2/10, p=0.039). La reescritura no cambia ninguna de las 8 autocontenidas y cuesta 248 ms de p50 en GPU, pero no pasa dos de sus cuatro criterios de aceptación. En la fase 3, un prompt `v2` con búsqueda doble (seguimiento literal y reescrita fusionados con RRF) se eligió en `dev` y acierta 10 de 12 en `test`, contra 11 del oráculo y 7 del literal (0/3, p=0.250); es la candidata. En el set v2 (115 conversaciones), en `dev` recupera 24 de 28 seguimientos contra 18 del literal (0/6 objetivos, p=0.031) y 23 del oráculo, sin cambiar ninguna de las 23 autocontenidas. En su corrida única en `test` recupera 17 de 25 contra 14 sin memoria (3/0, p=0.250) y 19 del oráculo, pierde 1 de 19 autocontenidas y no cambia la abstención: pasa los criterios de v2, aunque la mejora no es significativa. Se adoptó en el servicio el 2026-10-29.
- **Experimento N.º 7 (abstención por score)** — resuelto: no se adopta, `abstention.enabled` sigue en `false`. Estado vigente en `experiments/abstention/docs/README.md`, resultados en `experiments/abstention/results/abstencion_v1/summary.json`. Sobre las 135 preguntas, con el umbral elegido en una mitad y aplicado a la otra, ningún score (similitud del embedder, `bge-reranker-v2-m3` o `rrf_score`) evita una alucinación: `llama3.2:3b` ya se abstiene en 17 de las 20 preguntas sin respuesta, y las 3 restantes sacan scores tan altos como las preguntas con respuesta. El embedder (AUROC 0.581) bloquea 5 de 56 preguntas con respuesta en verificación; el cross-encoder separa mejor (AUROC 0.751), pero su umbral no atrapa ninguna. El LLM, en cambio, dice "No lo sé" en 33 de las 115 preguntas con respuesta.

La carpeta se renombró de `hybrid-serach` a `hybrid-search` (typo corregido) y los resultados de cada experimento ahora viven en su propia subcarpeta `results/` en vez de sueltos junto al `run.py`.

## Estructura

- `app/` — servicio FastAPI (`main.py`, `api/v1.py`, `schemas.py`, `deps.py`), logs JSON (`log.py`), API keys (`auth.py`) y su script (`manage_keys.py`), registro de consultas (`query_log.py`), trazas (`telemetry.py`), indexador incremental detrás del alias de Qdrant (`reindex.py`), `config/pipeline.yaml` y `Dockerfile` sin root.
- `corpus_demo/` — corpus versionado que indexa el servicio.
- `shared/` — código común: ingesta/chunking, retrieval (dense, BM25, RRF, rerank), pipeline del servicio (`pipeline.py`), clientes LLM (Ollama y Bedrock, más un modo sin modelo), spans OpenTelemetry (`tracing.py`), prompts, tracking, settings, el set de evaluación y el gate (`shared/eval`). `.importlinter` impide que el código de producción importe el de laboratorio.
- `experiments/chunking/` — experimento N.º 1: barrido de `chunk_size`/`overlap`, con tablas markdown separadas del embedding.
- `experiments/hybrid-search/` — experimento N.º 2: dense vs. BM25 vs. fusión híbrida (RRF).
- `experiments/reranking/` — experimento N.º 3: cross-encoder sobre el mejor retriever de la etapa anterior.
- `experiments/evaluation/` — experimento N.º 4: evaluación de respuestas (jueces LLM en la fase 1, verificación por oración contra etiquetas humanas en `generative/`).
- `experiments/sql/` — carga idempotente en Postgres del corpus servido, del set de preguntas y del benchmark del agente (`load_eval.py`).
- `experiments/agent/` — experimento N.º 5: agente con tool calling contra el pipeline fijo, con el mismo modelo y la misma recuperación.
- `experiments/conversation/` — experimento N.º 6: memoria conversacional, con el seguimiento literal, el historial concatenado y la pregunta reescrita por un LLM.
- `experiments/abstention/` — experimento N.º 7: abstención por score de recuperación (embedder, cross-encoder y RRF) contra la abstención del propio LLM.
- `agent/` — agente LangGraph (`python -m agent "pregunta"`): `qwen3:8b` con `buscar_documentos` del servidor MCP y `no_hay_respuesta` local, límite de pasos y tokens, y registro de cada llamada con su latencia.
- `mcp_server/` — servidor MCP por stdio (`python -m mcp_server.server`) con `buscar_documentos` (`/v1/retrieve`) y `preguntar` (`/v1/query`); se registra en Claude Code con `claude mcp add`.
- `migrations/` — migraciones de Alembic en dos ramas, en modo autocommit y con una sentencia DDL por migración. La rama `evaluacion` crea `documentos`, `chunks`, `preguntas`, `pregunta_documentos`, `corridas_eval`, `resultados_pregunta`, `veredictos`, `conversaciones_eval`, `turnos_eval` y seis vistas de análisis. La rama `servicio`, sin claves foráneas ni JSONB para que también corra en Aurora DSQL, crea `api_keys`, `sesiones`, `consultas`, `consulta_chunks`, `feedback`, `canario_ejecuciones`, el rol `app_writer` y cinco vistas de operación; `docker-compose-prod.yml` aplica solo esta rama (`alembic upgrade servicio@head`).
- `n8n/` — flujo del canario diario (`canario.json`) y el script que lo importa con sus credenciales (`importar.sh`).
- `detector/` — imagen de los servicios LettuceDetect (`detector_app.py`) y NLI (`nli_app.py`): FastAPI, versiones fijas, arranque offline.
- `tests/` — `unit/` (métricas, BM25/RRF, ingesta, parseo del juez, capas de grounding, carga de respuestas y chunks, pipeline, API, cliente LLM, indexado incremental, servidor MCP y agente; los corre el CI) `data/` (verifica que los gold spans sean literales en el corpus y que cada tipo de pregunta tenga los gold spans que le corresponden, y que los veredictos cargados en Postgres y el κ de su vista coincidan con el archivo de etiquetas: corre solo en local) e `integration/` (migraciones, restricciones, carga y vistas contra Postgres, y el flujo API → Qdrant → Postgres con API key: corre en local y en el job `integration` del CI).
